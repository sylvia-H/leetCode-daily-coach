## Concept

Tracing Execution Flow（執行流程追蹤）是不靠電腦、手動模擬程式逐行執行的技巧。做法是建立變數追蹤表（Trace Table）：每個變數一欄、每個時間點一列，程式每執行一行，就把被改動的變數新值填進新的一列。這是昨天「逐行畫盒子」的升級版：盒子只保留最後一次賦值的內容，追蹤表則把每一次改寫都留成一列快照，整條時間軸因此可以回溯。它之所以可靠，是因為程式的行為完全由「目前所有變數的值＋下一行程式碼」決定——只要每一步都照實記錄，你在紙上得到的軌跡必然與機器一致。除錯的本質因此可以重新定義：不是「猜哪裡有錯」，而是找出「預期軌跡」與「實際軌跡」分岔的第一個時間點；分岔點所在的那一行，就是錯誤的根源。這顆「腦內編譯器」（Mental Compiler）是後續所有演算法課的地基：讀不懂的程式碼，追一遍就懂了。

## Thinking

標準流程有四步。第一，寫下所有輸入參數與區域變數的初始值，作為表格第一列。第二，逐行執行：遇到賦值就更新該變數的欄位；遇到條件判斷，把當前列的實際值代入條件式算出真假，由結果決定走哪個分支——絕不能用「我覺得應該走這裡」代替計算。複合條件也照機器的規則走：由左而右、能短路就短路，左側已能決定結果時右側根本不會執行，這常是預期中的副作用沒發生的原因。第三，迴圈每執行一輪就新增一列，直到終止條件成立。第四，把最後一列與預期輸出比對；不一致時，從頭找出第一個與預期不符的格子。舉個最小例子：`total = 0`，依序走訪 `[3, 1, 4]`，只有奇數才累加。表格逐列是：`v=3` 為奇數，`total` 變 3；`v=1` 為奇數，`total` 變 4；`v=4` 為偶數，條件不成立，`total` 維持 4。三列表格就完整重現了整段程式的行為，任何一格算錯都會與機器結果分岔。

## Pattern Recognition

啟動時機有兩類。一是除錯：程式結果不如預期、卻不知道錯在哪一行——此時任何「用看的」都比不上逐行追蹤可靠。二是讀碼：面對含有巢狀迴圈（Nested Loops）、指標（Pointer）移動、遞迴（Recursion）或多重條件的陌生程式碼，追蹤表能把看不見的狀態變化攤開成看得見的表格。反過來說，若程式只是一條沒有分支與迴圈的直線，直接讀完即可，不必動用表格——追蹤的報酬率來自狀態的複雜度。

## Common Mistakes

第一，跳著讀與心算合併：一次「看完」好幾行、在腦中把效果加總，工作記憶一滿就出錯——追蹤的價值正在於逐行落筆，讓紙張代替腦袋記住狀態。第二，用預期反推分支：不代入實際值計算條件真假，而是看著「程式應該要對」的期待選分支，這樣追出來的是想像中的程式，永遠找不到 Bug。第三，快照沒有時間概念：直接把新值蓋掉表上舊值，事後想檢查第幾輪出錯時已無從對照——每個時間點都應該是獨立的一列。第四，只追主路徑：邊界輸入（空陣列、單一元素）往往走的是另一條分支，只追一組「正常」輸入，會漏掉真正出錯的路徑。

## Complexity

O(n) / O(1)。追蹤的時間成本隨執行步驟數線性成長：程式跑幾步，表格就有幾列。空間上，表格的欄位數只等於變數個數、與輸入規模無關；若只保留當前一列，狀態本身就是常數大小——但除錯時建議保留完整歷史，用少量紙面空間換取隨時回溯任一時間點的能力。

## Digest

Tracing Execution Flow 用變數追蹤表手動模擬程式：每個變數一欄、每個時間點一列，逐行執行，遇賦值就填新列、遇條件就把當前值代入算真假。程式行為完全由「當前狀態＋下一行」決定，照實記錄的紙上軌跡必然與機器一致，因此除錯就是找出預期與實際軌跡分岔的第一格。例如 `total = 0` 走訪 `[3, 1, 4]` 只加奇數：三列分別得 3、4、4，任何一格算錯都會現形。最忌心算合併多行與用預期反推分支——追蹤要的是機器的答案，不是你的想像。

## TypeScript Tip

手動追完後，在迴圈內用 `console.log` 印出每一輪的快照，逐列比對你的表格是否與機器一致：

```typescript
function sumOdds(nums: number[]): number {
  let total = 0;
  for (let i = 0; i < nums.length; i++) {
    const v = nums[i]!;
    if (v % 2 === 1) total += v;
    console.log(`i=${i} v=${v} total=${total}`); // 與手動表格逐列比對
  }
  return total;
}
if (sumOdds([3, 1, 4]) !== 4) throw new Error("assertion failed");
if (sumOdds([]) !== 0) throw new Error("assertion failed");
```

`noUncheckedIndexedAccess` 下 `nums[i]` 的型別是 `number | undefined`，用 `!` 收斂前請先確認索引在範圍內——這正是追蹤表能幫你驗證的事。

## Python Tip

在迴圈內用 `print` 印出快照，與手動表格逐列對照，每行輸出就是一個時間點：

```python
def sum_odds(nums: list[int]) -> int:
    total = 0
    for i, v in enumerate(nums):
        if v % 2 == 1:
            total += v
        print(f"i={i} v={v} total={total}")  # 與手動表格逐列比對
    return total

assert sum_odds([3, 1, 4]) == 4
assert sum_odds([]) == 0
```

熟練 `print` 對表之後，若需要互動式逐行檢查，內建的 `pdb` 可以在任一行停下來查看變數——它做的事和你的紙上追蹤表完全相同。

## Takeaway

程式走向由變數當前值決定：逐行記錄快照、代入條件求真假，用追蹤取代猜測。
