## Concept

程式設計的第一步不是寫程式碼，而是把模糊、龐大的現實問題轉化為精確、可執行的指令序列——這就是 Computational Thinking（計算思維）。它最核心的工具是 Decomposition（問題拆解）：把一個無從下手的大問題，沿著清楚的邊界切成幾個獨立的小步驟。以「泡一杯手沖咖啡」為例，「把咖啡泡好」這句話對機器（或第一次泡咖啡的人）毫無意義；但拆成「一、把水加熱到 92 度；二、磨好 15 克咖啡豆放入濾杯；三、分三次注水、每次 60 毫升」之後，每一步都能直接照做。「可執行」的判準就在這裡：步驟有具體數字與明確的完成條件，不依賴讀者腦補，任何人照做都會得到同樣的結果。描述一個任務的演化時，抓住三個錨點即可：起始狀態（手上有什麼）、轉換步驟（做了什麼）、終止狀態（結束時保證什麼）。

## Thinking

最有效的拆解順序是「先定義終點，再反推最小可行步驟」。順著想（我先做什麼、再做什麼）容易發散成流水帳；倒著想則會自動濾掉不必要的動作——先寫下終止狀態，例如「輸出一杯 300 毫升的咖啡」，再反問「要得到它，前一步必須完成什麼？」如此一路反推回起始狀態。對每個推出來的步驟檢查兩件事：它是否精確（有具體數值或明確的完成條件，而不是「差不多」「適量」）；它是否獨立（不需要同時想著別的步驟也能做完）。全部通過檢查後，大問題就變成一串可以逐一擊破的小任務，寫程式只是把它們翻譯成語法而已。

## Pattern Recognition

當你面對不知從何下手的需求、規格只有一句模糊描述（「幫我做個訂單系統」），或是盯著空白編輯器十分鐘寫不出第一行時，就是套用 Decomposition 的訊號。判斷方法：問自己「這個任務能不能用三個階段講完——起始狀態是什麼、經過哪些轉換、終止狀態保證什麼？」講不出來，代表問題還太大或太模糊，需要繼續往下切；講得出來，每個階段又能用同樣方式再切細，直到每一步都小到「一眼就知道怎麼做」為止。

## Common Mistakes

第一個常見錯誤是急著動手寫程式碼，跳過拆解直接實作。表面上進度飛快，實際上是把「想清楚」的成本延後到除錯階段——邏輯糾纏在一起的巨型函式，出錯時你連該檢查哪一段都不知道。第二個錯誤是步驟不精確：寫下「處理使用者輸入」這種步驟等於沒拆，因為它仍然無法直接執行；精確的版本是「若輸入為空字串則回傳錯誤訊息，否則去除前後空白」。第三個錯誤是顆粒度失當——切得太粗，單一步驟仍複雜到難以下手；切得太細，組裝碎片的成本反而超過問題本身。合適的判準是：每一步都能獨立完成、也能獨立驗證。

## Complexity

O(1) / O(1)。本課是思維方法而非具體演算法：拆解發生在紙上與腦中，不佔用程式的執行時間與記憶體；日後每個子步驟實作出來的複雜度，由該步驟選用的演算法各自決定。

## Digest

程式設計的第一步是 Decomposition：把模糊的大問題拆成精確、可獨立執行的小步驟。方法是「先定義終點，再反推最小可行步驟」——先寫下終止狀態，一路反問「前一步必須完成什麼」。以手沖咖啡為例：「把咖啡泡好」無法執行，拆成「水加熱到 92 度 → 磨 15 克豆 → 分三次各注水 60 毫升」後，每一步都有具體數字與完成條件，任何人照做結果都相同。檢查拆解品質的方式：能否用「起始狀態 → 轉換步驟 → 終止狀態」三個階段把任務講完；講不出來就是還太模糊，繼續往下切。最常見的錯誤是急著動手寫程式碼——那只是把「想清楚」的成本延後到除錯階段，以更貴的方式償還。

## TypeScript Tip

動手寫 TypeScript 之前，先把拆解出的步驟寫成註解，再逐一翻譯成程式碼——註解就是你的執行藍圖：

```typescript
function brewTime(pours: number): number {
  // 拆解：1. 每次注水 45 秒 → 2. 注水之間各悶蒸 30 秒 → 3. 加總
  const pouring = pours * 45;
  const waiting = (pours - 1) * 30;
  return pouring + waiting;
}
if (brewTime(3) !== 195) throw new Error("assertion failed");
if (brewTime(1) !== 45) throw new Error("assertion failed");
```

註解與程式碼一一對應，之後任何一步出錯，都能立刻定位到對應的那一行。

## Python Tip

Python 的語法貼近虛擬碼（pseudocode），很適合把拆解草稿直接寫成可執行的步驟清單：

```python
def brew_time(pours: int) -> int:
    pouring = pours * 45        # 步驟一：每次注水 45 秒
    waiting = (pours - 1) * 30  # 步驟二：注水之間各悶蒸 30 秒
    return pouring + waiting    # 步驟三：加總得到總秒數

assert brew_time(3) == 195, "assertion failed"
assert brew_time(1) == 45, "assertion failed"
```

草擬階段不必急著最佳化：先讓每一行對應一個拆解出的步驟，邏輯對了再談效率。

## Takeaway

先定義終點再反推最小可行步驟，把模糊的大問題拆成精確、可獨立執行與驗證的小步驟。
