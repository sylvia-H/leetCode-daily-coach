# Feature Specification: Walking Skeleton（垂直切片：從課程內容到 Discord 的全鏈路打穿）

**Feature Branch**: `001-walking-skeleton`

**Created**: 2026-07-19

**Status**: Draft

**Input**: User description: "feature 001-walking-skeleton"

## 背景與目的

本 Feature 是 LeetCode Daily Coach 的第一個垂直切片（對應 `docs/spec.md` §22.5 F1、§23 Phase 0、里程碑 M0）。

它**不建立正式的 Curriculum schema、DAG、題庫或內容產線**，而是用**一篇手寫教材 + 一份硬編的極短課表**，
把「每日排程 → 取出今天該上的課 → 組裝課程 → 渲染成 Discord 版面 → 推播 → 記錄進度」這條完整鏈路打通，
以便在**真實 Discord 環境**上提早驗證三件紙上設計驗不了的事：

1. Discord 單則訊息的字元上限與版面觀感（讀起來像不像「一堂課」）。
2. 同一天重複觸發的去重行為（雙排程補跑機制）。
3. 進度狀態獨立保存於專用狀態分支的流程是否可行。

驗證結果會回頭影響 F2 之後的 schema 與教材設計，因此**先打穿、再回頭定規格**是本 Feature 的核心價值。

## Clarifications

### Session 2026-07-19

- Q: 本 Feature 的題目資料（題號、標題、連結、難度、whyThisPattern、Hint）以什麼形式提供？ → A: 極小資料檔（3 題），置於 `docs/spec.md` §17 既定的題庫路徑，欄位為 §12.1 的最小子集；F1 只讀不驗證 schema
- Q: 手寫教材（FR-001）如何轉成推播用的課程物件？ → A: 實作最小組裝器，實際解析教材的固定區塊，但只取推播用區塊（Digest / TS Tip / Python Tip / Exit Criteria / Takeaway）與必要 metadata；閱讀用區塊存在但不解析
- Q: 三個 Session 共用同一篇教材時，「學習路徑（昨天／今天／明天）」欄位顯示什麼？ → A: 硬編一張「課程序號 → 前／今／後觀念名稱」小表，三課各顯示不同的鄰近觀念名稱；第 1 課省略「昨天」、第 3 課仍顯示「明天」
- Q: 預覽模式（DRY_RUN）與同日去重／強制模式（FORCE）如何交互？ → A: 預覽模式略過同日去重判斷（永遠完整組裝並輸出渲染結果）；與強制模式同時開啟時「不推播、不寫狀態」優先，行為與單獨預覽相同

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 早上在 Discord 收到一堂真的課 (Priority: P1)

學習者手動觸發（或等待每日排程）後，在自己的 Discord 頻道收到一則排版完整的課程訊息：
包含今日觀念的精華說明、Pattern 與複雜度標示、TypeScript / Python 各一則實戰要點、
1～3 題可點擊的 LeetCode 題目（題號 + 標題 + 難度 + 為什麼適合此 Pattern + Hint）、
學習路徑（昨天 / 今天 / 明天）、Exit Criteria 勾選清單，以及一句 Takeaway。

**Why this priority**: 這是整個產品對使用者的唯一交付形式。看得到這則訊息，才算證明鏈路可行、
版面可讀、字元預算的設計成立；其餘所有 Story 都是圍繞它的保護機制。

**Independent Test**: 只實作這一個 Story，手動觸發一次即可完整驗證——學習者在手機上收到訊息、
內容可讀、連結可點，即交付了「每日一堂課」的核心價值。

**Acceptance Scenarios**:

1. **Given** 已設定一個 Track 的推播頻道且進度為第 1 課，**When** 手動觸發推播，**Then** 該頻道收到一則
   課程訊息，內含觀念精華、Pattern / 複雜度 / 預估時間、TypeScript 與 Python 要點、題目清單、學習路徑、
   Exit Criteria 與 Takeaway。
2. **Given** 同上，**When** 訊息送達，**Then** 每一題都以「題號 + 官方標題」的可點連結呈現並可正確開啟
   LeetCode 頁面，且訊息中**不含**任何 LeetCode 題目的完整題敘。
3. **Given** 同上，**When** 檢查送出的訊息，**Then** 其全部文字總量不超過平台單則訊息上限，且落在本專案
   自訂的安全預算內。
4. **Given** 完全沒有設定任何推播頻道，**When** 觸發推播，**Then** 流程立即以失敗結束並明確指出是設定錯誤，
   不進行任何推播或狀態變更。

---

### User Story 2 - 學完一課後進度自動往前，且不會因故障而跳課 (Priority: P2)

推播成功後，該 Track 的進度自動前進到下一課，並記錄推播時間與已完成的觀念；
進度資料保存在與程式碼分離的專用狀態分支，不污染主分支歷史。推播失敗時進度**不前進**，
隔天會重推同一課（漏跑不跳課）。

**Why this priority**: 沒有進度推進，使用者每天只會收到同一課，產品失去「循序漸進」的意義；
而「失敗不前進」是避免使用者永久錯過某一課的關鍵保護。

**Independent Test**: 連續觸發兩次（第二次繞過同日去重），確認收到的是第 1 課與第 2 課；
再模擬一次推播失敗，確認進度停在原地。

**Acceptance Scenarios**:

1. **Given** 進度為第 1 課，**When** 推播成功，**Then** 進度更新為第 2 課、記錄本次推播時間、
   將本課觀念加入已完成清單，且變更被保存到專用狀態分支。
2. **Given** 進度為第 1 課，**When** 推播失敗，**Then** 進度仍為第 1 課、發出一則紅色錯誤告警、
   流程以非零狀態結束。
3. **Given** 狀態中尚未出現某個已啟用的 Track，**When** 執行推播，**Then** 系統自動為該 Track 建立初始進度
   （第 1 課、尚未推播過）並照常推播第 1 課。
4. **Given** 已累積多次推播紀錄，**When** 進度再次更新，**Then** 歷史紀錄維持在上限筆數內（滾動保留），
   不會無限成長。
5. **Given** 一次執行處理完所有已啟用 Track，**When** 保存狀態，**Then** 只產生**一次**狀態存檔與**一次**提交，
   且該提交只出現在專用狀態分支，主分支不含任何自動產生的狀態提交。

---

### User Story 3 - 同一天不會被重複打擾 (Priority: P3)

系統每天有兩次排程（主推與補跑）。若某 Track 今天已經推播過，補跑時該 Track 會被跳過；
若主推當天被平台跳過或失敗，補跑仍會補上今天的課。需要補推或除錯時，可用強制模式繞過此判斷。

**Why this priority**: 雙排程是為了對抗排程平台的不可靠性，但沒有去重就會造成一天收到兩則相同課程；
這是使用者立即有感的體驗瑕疵，但在單次推播尚未跑通前不具意義，故列於 P3。

**Independent Test**: 同一天內連續觸發兩次，確認第二次被跳過且進度未變；再以強制模式觸發，確認會推播。

**Acceptance Scenarios**:

1. **Given** 某 Track 今天（台北時區）已成功推播，**When** 當天稍後再次觸發，**Then** 該 Track 被跳過、
   不推播、進度不變，且流程以成功狀態結束。
2. **Given** 某 Track 最近一次推播是昨天（台北時區），**When** 今天觸發，**Then** 正常推播下一課。
3. **Given** 某 Track 今天已推播過，**When** 以強制模式觸發，**Then** 忽略去重判斷照常推播，並照常更新進度。
4. **Given** 某 Track 最近一次推播時間落在台北時間深夜、以世界標準時間看仍屬前一日（或反之），
   **When** 進行去重判斷，**Then** 一律以台北時區的日曆日為準，不因時區換算而誤判。

---

### User Story 4 - 不打擾任何人也能先看到版面 (Priority: P4)

開發或調整版面時，可用「預覽模式」跑完整條流程（取課 → 組裝 → 渲染），把渲染結果輸出到執行紀錄，
但**不推播到 Discord、也不改動任何進度**。

**Why this priority**: 讓版面調整不必消耗真實推播、也不會污染進度，是開發期的效率工具，
對終端使用者無直接價值，故列為最低優先。

**Independent Test**: 以預覽模式觸發，確認執行紀錄中可看到完整渲染結果，且頻道無新訊息、進度未變。

**Acceptance Scenarios**:

1. **Given** 已設定推播頻道且進度為第 1 課，**When** 以預覽模式觸發，**Then** 執行紀錄輸出完整的課程渲染結果，
   Discord 頻道**沒有**新訊息，進度**仍為**第 1 課，且不產生任何狀態提交。
2. **Given** 預覽模式，**When** 渲染結果超出字元預算，**Then** 執行紀錄以 **§14.5 的每一個預算項目為單位**
   （Digest / TS Tip / Python Tip / 每題 / Exit Criteria / Takeaway / 學習路徑 / 總量）逐項標示
   名稱、實際字元數、上限與是否超限，供調整版面。
3. **Given** 某 Track 今天（台北時區）已成功推播，**When** 以預覽模式觸發，**Then** 該 Track **不被跳過**，
   執行紀錄照常輸出完整渲染結果，且頻道無新訊息、進度不變。
4. **Given** 同時開啟預覽模式與強制模式，**When** 觸發，**Then** 行為與單獨開啟預覽模式相同——
   輸出渲染結果、不推播、不寫入狀態，且不因選項衝突而失敗。

---

### Edge Cases

- **沒有任何 Track 被啟用**（全部推播頻道皆未設定）：立即以設定錯誤失敗，不推播、不改狀態。
- **推播被對方拒絕**（頻道位址失效、限流、伺服器錯誤）：視為該 Track 推播失敗——進度不前進、發紅色告警、
  流程以非零狀態結束。
- **告警本身也送不出去**（頻道位址不可用）：仍必須留下錯誤紀錄並以非零狀態結束，不得無聲失敗；
  且**不得因告警失敗而中斷其餘 Track 的處理**（見 FR-010c）。
- **硬編課表被走完**（進度超出本 Feature 的極短課表範圍）：不循環回第 1 課、不推播，改為發出告警並以非零
  狀態結束（fail loud）——提醒使用者這是刻意的臨時課表。
  此情境 MUST 視為**該 Track 的失敗**（而非全域性失敗）：僅該 Track 不推播、進度不前進，
  其餘 Track MUST 照常處理，全部處理完後才以非零狀態結束。
- **題目資料不一致**（觀念查無對應題目、對應題號在資料檔中不存在、題數為 0 或超過 3）：
  視為該 Track 失敗——發紅色告警、進度不前進、繼續其餘 Track（見 FR-003b），
  MUST NOT 靜默截斷題數或略過缺漏的題目。
- **狀態檔不存在或內容缺少某個已啟用 Track**：自動補建該 Track 的初始進度，不中斷流程。
- **同一個觀念被重複推播**（本 Feature 三個 Session 共用同一篇教材）：已完成觀念清單 MUST 去重，
  同一觀念只留一筆，不因重複推播而累積重複項目。
- **狀態檔內容損毀無法解析**：視為全域性失敗，立即以非零狀態結束，不覆寫既有狀態檔（避免毀掉唯一權威狀態）。
- **狀態分支提交衝突**（外部同時修改）：自動重新同步後重試數次才放棄；放棄時明確報錯。
- **渲染結果超出平台字元上限**：必須在送出前被擋下並報錯，而非讓推播被平台拒絕。
- **主推排程當日未執行**：補跑排程必須能補上當天的課，且不會造成一天兩推。

## Requirements *(mandatory)*

### Functional Requirements

**課程內容與課表（本 Feature 為臨時形式，F2–F5 取代）**

- **FR-001**: 系統 MUST 提供**一篇手寫的完整教材**，內含 `docs/spec.md` §10 規定的全部固定區塊
  （含推播用的 Digest / TypeScript Tip / Python Tip、Takeaway），作為本 Feature 的推播素材；
  該教材 MUST 遵守 §14.5 的各區塊字元預算，使字元限制的驗證具有代表性。
  此教材為臨時產物，MUST 在檔案內明確標示其臨時性與被取代的時機（**F7 內容產線上線後由生成物取代**）。
- **FR-001a**: 教材撰寫 MUST 遵守 `docs/spec.md` §11 的語言規範：正文以繁體中文撰寫，
  但技術術語、Pattern 名稱、API / 類別 / 函式名與程式碼 MUST 保留英文（Sliding Window、`O(n)`、`bisect` 不譯）。
- **FR-001b**: 教材 MUST 以 frontmatter 提供推播所需的 metadata，至少涵蓋：觀念 id、標題、所屬 Module、
  Pattern 標籤、複雜度標籤、預估時間、Exit Criteria 清單。**Pattern 標籤與複雜度標籤 MUST 由 frontmatter
  明確提供，MUST NOT 由程式從正文推導**（正文為敘述性散文，啟發式抽取違反確定性原則）。
- **FR-001c**: 教材各區塊符合 §14.5 預算**不等於**渲染結果必然合規——渲染會再加入標題、emoji 與版面文字。
  最終判準 MUST 以 FR-006 的渲染結果為準；教材端預算僅為使其可能達標的必要條件。
- **FR-002**: 系統 MUST 提供一份**硬編的極短課表**（3 個 Session），用於驗證進度推進。
  三個 Session MUST 皆為 concept 類型且**共用 FR-001 的同一篇教材**，彼此只有課程序號不同——
  本 Feature 驗證的是流程與版面，不是內容多樣性。
  此課表為臨時產物，MUST 在檔案內明確標示其臨時性與被取代的時機（F4 課表生成器上線即淘汰）。
- **FR-003**: 題目的題號、官方標題、連結與難度 MUST 由程式從資料來源帶入並原樣呈現，
  MUST NOT 轉載 LeetCode 題目的完整題敘。
- **FR-003a**: 題目資料 MUST 以**獨立的資料檔**提供（本 Feature 僅需涵蓋所用的 3 題），
  存放於 `docs/spec.md` §17 既定的題庫路徑，欄位採 §12.1 的**最小子集**
  （題號、官方標題、連結、難度、為什麼適合此 Pattern、Hint）。
  本 Feature MUST 只讀取此檔、MUST NOT 對其做 schema 驗證或建立 Concept ↔ Problem 逆向對應（屬 F3）；
  題目資料 MUST NOT 硬編於程式常數或教材 frontmatter 中，以確保 F3 只需擴充資料而不需改動讀取路徑。
  此資料檔為臨時規模的產物，MUST 標示其僅涵蓋本 Feature 所需題目（**F3 擴充為完整題庫**）。
- **FR-003b**: 每個觀念對應哪些題目 MUST 由題目資料檔中的**觀念 → 題號對照**決定，
  MUST NOT 由教材內容或程式邏輯推導。對應結果 MUST 為 **1～3 題**；
  若查無對應、對應題號在資料檔中不存在，或題數為 0 或超過 3，MUST 視為該 Track 失敗並發出告警
  （fail loud），MUST NOT 靜默截斷題數或略過缺漏題目。
  題數合法性的**唯一權威守門點 MUST 為此對應階段**；渲染後的字元預算檢查雖亦含題數上限，
  但僅為 defense-in-depth，MUST NOT 被當作主要判準（避免兩處各自定義錯誤型態與訊息）。
- **FR-003c**: 本 Feature 的題目資料由人工填寫，其**題號、標題、連結、難度的正確性 MUST 經人工核對**
  （連結可正確開啟對應 LeetCode 頁面），並作為 SC-001 的前提；F3 起改由題庫維護流程保證。

**組裝與渲染**

- **FR-004**: 系統 MUST 依「Track + 目前進度」組裝出一個完整的**課程物件**，其中所有欄位皆為既有的凍結內容，
  MUST NOT 有任何欄位需要在推播當下向外部生成服務取得。
- **FR-004a**: 組裝 MUST 由**實際解析教材檔的固定區塊**取得內容，MUST NOT 把課程物件硬編為程式常數
  ——「教材檔 → 課程物件」是本 Feature 要打穿的鏈路一環。本 Feature 的解析範圍 MUST 限於：
  - **必要區塊**（正文，恰為四個）：**Digest、TypeScript Tip、Python Tip、Takeaway**
  - **必要 metadata**（frontmatter，見 FR-001b）：觀念 id、標題、Module、Pattern 標籤、複雜度標籤、
    預估時間、**Exit Criteria**

  閱讀用區塊（Concept / Thinking / Pattern Recognition / Common Mistakes / 各語言 Corner 等）
  MUST 存在於教材檔中但**不被解析**（留待 F5 擴充）。
  > **注意**：Exit Criteria MUST 取自 frontmatter，**不是**正文區塊——它是結構化清單而非散文，
  > 由 frontmatter 提供才能確定性地逐條呈現為 checklist。
- **FR-004b**: 解析器 MUST 在缺少 FR-004a 所列**任一必要區塊或必要 metadata** 時明確報錯
  （錯誤訊息 MUST 指名缺少的項目）並使該 Track 視為失敗，MUST NOT 以空字串或預設值靜默帶過；
  但本 Feature MUST NOT 對教材 metadata 施行型別 / 值域的 schema 驗證（屬 F2），只檢查「存在且非空」。
- **FR-004c**: 教材中出現 FR-004a 未列舉的區塊時，解析器 MUST **忽略**該區塊且 MUST NOT 因此失敗
  （保留 F5 擴充解析範圍的空間）。本 Feature 亦 MUST NOT 檢查「不解析」的閱讀用區塊是否存在
  ——該檢查屬 F5 的內容 Gate 職責。
- **FR-005**: 渲染 MUST 為無狀態的純函式——同一個課程物件 MUST 產出完全相同的推播內容；
  渲染階段 MUST NOT 讀取課表、題庫、檔案或進度狀態。
- **FR-006**: 渲染結果 MUST 符合平台限制與本專案自訂預算：單則訊息全部文字總和 ≤ 6,000（平台硬限）
  且 ≤ 5,500（自訂安全上限），各區塊並 MUST 符合 §14.5 的個別預算；
  超限 MUST 在送出前被偵測並視為該 Track 失敗。
  **MUST NOT 自動截斷任何內容以求通過**——靜默裁切等同無聲失敗，違反 fail loud 原則。
- **FR-006a**: 字元總量的**計算口徑** MUST 依 `docs/spec.md` §14.5 的定義（計入欄位與長度單位），
  使 SC-002 的「通過率 100%」有唯一判準；本 Feature 與未來的 CI Gate MUST 採用同一口徑。
- **FR-006b**: 預算檢查 MUST 一併涵蓋平台的**結構性上限**（單一 Embed 的標題長度、描述長度、
  欄位數量、單一欄位的名稱與值長度，以及單則訊息的 Embed 數量），而不只是文字總量與各區塊預算；
  任一結構性上限超出 MUST 與預算超限同等處置（送出前擋下、該 Track 失敗）。
  **理由**：這些上限是平台會直接拒絕請求的硬限制，若只檢查總量，超限會在送出時才由平台回報，
  等同把可在送出前攔下的錯誤延後到推播階段。
- **FR-007**: 課程版面 MUST 包含下列元素，且 MUST 依此順序呈現
  （**觀念相關內容 MUST 先於題目**，以落實 Concept-first 原則）：
  1. 觀念精華
  2. Pattern / 複雜度 / 預估時間
  3. TypeScript 與 Python 要點
  4. 1～3 題題目（連結 + 難度 + 為什麼適合此 Pattern + Hint）
  5. 學習路徑（昨天 / 今天 / 明天）
  6. Exit Criteria 勾選清單
  7. Takeaway

  各元素的字元預算依 §14.5；其中**學習路徑套用 §14.5 的「學習路徑 footer」預算（≤ 200）**，
  不因其實際以何種版面元件呈現而改變預算歸屬。
- **FR-007a**: 學習路徑的三個觀念名稱 MUST 隨課程序號變化——本 Feature 以一張硬編的
  「課程序號 → 前 / 今 / 後觀念名稱」對照表提供，三個 Session MUST 各顯示不同的鄰近觀念名稱，
  MUST NOT 三課皆顯示同一組字串（否則版面觀感的驗收失去代表性）。
  第 1 課 MUST 省略「昨天」一行；第 3 課 MUST 仍顯示「明天」（預告後續內容）。
  對照表中的觀念名稱 **MAY 指向本 Feature 尚未建立的後續 Concept**（本 Feature 只有一篇教材，
  「明天」必然如此）；這些名稱僅為版面顯示字串，MUST NOT 被解讀為內容存在性的承諾。
  此對照表為臨時產物，F2 接上 DAG 後 MUST 改由 prerequisite / next 取得。
- **FR-007b**: 題目的 **Hint 為選填**。缺少 Hint 時，版面 MUST 省略該題的 Hint 段落（含其分隔符），
  MUST NOT 顯示空白欄位或佔位文字。
- **FR-007c**: 課程版面 MUST 依教材所屬 Module 套用對應顏色。Module → 色碼的對照 MUST 為
  **確定性的常數對照表**（同一 Module 恆為同一色）；查無對應 Module 時 MUST 使用明確定義的預設色，
  MUST NOT 隨機或依執行時資訊決定顏色。

**推播與失敗處理**

- **FR-008**: 系統 MUST 以「該 Track 的推播頻道設定非空」作為該 Track 的啟用開關；
  移除設定即停用，MUST NOT 需要修改程式或另設開關。
- **FR-009**: 系統 MUST 依固定順序逐一處理已啟用的 Track（單一執行流程，MUST NOT 平行處理），
  且單一 Track 的失敗 MUST NOT 中斷其餘 Track 的處理。
- **FR-010**: 任一核心步驟失敗時，系統 MUST 對對應頻道發出一則紅色告警訊息（若該頻道可用）、
  留下錯誤紀錄，並使整體流程以非零狀態結束；MUST NOT 無聲失敗。
- **FR-010a**: **告警的發送責任 MUST 歸屬於推播程式本身**——單一 Track 失敗與全域性失敗
  （無任何頻道設定、狀態檔位置未設定、狀態檔損毀）皆 MUST 由程式以**同一套告警渲染邏輯**發出，
  MUST NOT 由排程平台的設定檔另行拼組告警版面（同一責任兩套實作會使版面隨時間漂移）。
  全域性失敗的告警對象為**第一個已設定的頻道**；若連一個頻道都沒有設定，則 MUST 僅留下錯誤紀錄
  並以非零狀態結束（無處可發不構成無聲失敗）。
- **FR-010b**: 排程平台層級 MAY 保留一道**最後防線通知**，用於程式根本沒能啟動的情境
  （相依安裝、編譯或環境取得失敗）。此通知 MUST 為**極簡純文字**且 MUST NOT 重製課程或告警的版面結構，
  以免與 FR-010a 的告警形成雙軌實作。
- **FR-010c**: **告警本身送不出去時**（頻道位址失效、平台拒絕），系統 MUST 留下錯誤紀錄、
  仍將該次失敗計入整體結果（非零狀態結束），且 MUST NOT 因告警失敗而中斷其餘 Track 的處理。
- **FR-011**: 每日推播流程 MUST 能在**完全沒有任何 LLM 服務憑證**的環境下端到端成功執行。

**進度狀態**

- **FR-012**: 系統 MUST 以**每個 Track 各自一份進度**的結構保存狀態，內含：下一課序號、最近推播時間、
  已完成觀念清單、推播歷史。
- **FR-013**: 某 Track 的課程序號 MUST 只在該 Track 推播成功後才前進一課；推播失敗或被跳過時 MUST NOT 前進。
- **FR-014**: 推播歷史 MUST 設有筆數上限並滾動保留（上限 30 筆），MUST NOT 無限成長。
- **FR-015**: 狀態中不存在的已啟用 Track，系統 MUST 自動補建初始進度（第 1 課、尚未推播過）。
- **FR-016**: 全部 Track 處理完畢後，系統 MUST 只進行**一次**狀態存檔；狀態變更 MUST 只提交至**專用狀態分支**，
  MUST NOT 提交至主要開發分支。
- **FR-017**: 狀態分支的提交若因外部並行修改而衝突，系統 MUST 自動重新同步後重試，
  **重試上限固定為 3 次**（衝突來源僅有相隔 30 分鐘的雙排程極罕見重疊，3 次已足夠）；
  重試耗盡才報錯，MUST NOT 無限重試。
- **FR-018**: 調整學習進度的唯一官方方式 MUST 是直接編輯狀態分支上的進度資料；
  MUST NOT 另設「起始課數」之類的設定項。

**排程與去重**

- **FR-019**: 系統 MUST 每日以兩個時點自動執行（台北時間清晨 06:07 主推、06:37 補跑），並支援手動觸發。
- **FR-020**: 每次執行、對每個已啟用 Track，系統 MUST 以該 Track 最近推播時間換算成**台北時區日曆日**進行判斷；
  若等於今日則跳過該 Track（跳過不視為失敗）。預覽模式與強制模式為此判斷的例外（見 FR-021a、FR-021）。
- **FR-021**: 手動觸發 MUST 提供「預覽模式」與「強制模式」兩個選項；
  預覽模式 MUST 完整執行組裝與渲染但不推播、不寫入狀態；強制模式 MUST 繞過同日去重判斷但照常寫入狀態。
- **FR-021a**: 預覽模式 MUST 自行略過同日去重判斷——即使該 Track 今天已推播過，預覽模式仍 MUST 完整組裝
  並輸出渲染結果（去重防的是重複打擾，而預覽不推播亦不寫狀態，該風險不存在）。
- **FR-021b**: 兩種模式同時開啟時，MUST 以預覽模式為準（不推播、不寫入狀態），行為與單獨開啟預覽模式完全相同；
  MUST NOT 視為設定衝突而失敗。

**機密與環境**

- **FR-022**: 推播頻道位址等機密 MUST 只透過執行環境的機密管理提供，MUST NOT 出現在版本庫或任何產出物中。
- **FR-023**: 缺少任一必要設定時，系統 MUST 立即失敗並明確指出缺少哪一項，MUST NOT 帶著不完整的設定繼續執行。
- **FR-024**: 本 Feature MUST 交付一份**一次性環境建置說明文件**，涵蓋：專用狀態分支的建立、
  Discord 頻道與推播位址的取得、機密設定項的登錄；並 MUST 附上**初始進度資料的樣板**
  （含三個 Track 的初始結構，供建立狀態分支時直接使用）。
  文件所述步驟由使用者**手動執行一次**；本 Feature MUST NOT 提供自動代為建立分支或頻道的程式。
- **FR-025**: FR-024 的說明文件 MUST 可被實際依循完成——由使用者照文件走一遍且環境成功就緒，
  即為本項的驗收方式。

### Key Entities

- **課程（Lesson）**：組裝階段的產物、渲染階段的唯一輸入。包含課程序號、Session 類型、Track、
  觀念內容（標題、精華、雙語言要點、Takeaway、Exit Criteria、Pattern / 複雜度 / 預估時間、模組顏色）、
  題目清單、學習路徑（前/今/後）。所有欄位皆為既有的凍結內容。
- **課表項目（Session Plan）**：課程序號 → 該日要上的內容（Session 類型 + 對應觀念）的對照。
  本 Feature 為硬編的 3 筆臨時資料。
- **題目（Problem）**：題號、官方標題、連結、難度、為什麼適合此 Pattern、Hint（**選填**，見 FR-007b）。
  本 Feature 以獨立資料檔提供（3 題、§12.1 最小子集），只讀不驗證（見 FR-003a）；
  觀念 → 題號的對應亦由該檔提供（見 FR-003b）。
- **Track 進度（Track State）**：下一課序號、最近推播時間、已完成觀念清單、推播歷史（滾動上限 30 筆）。
- **教材（Article）**：手寫的完整觀念文章，含 §10 全部固定區塊與推播所需的 frontmatter metadata；
  由組裝階段實際解析，但只取四個推播用正文區塊（Digest / TypeScript Tip / Python Tip / Takeaway）
  與 frontmatter metadata（含 Exit Criteria）——解析範圍見 FR-004a。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 手動觸發一次後，學習者在 3 分鐘內於自己的 Discord 頻道收到一則課程訊息，
  且訊息中每一個題目連結皆可正確開啟對應的 LeetCode 頁面。
- **SC-002**: 送出的課程訊息全部文字總量 ≤ 5,500 字元（平台硬上限為 6,000），
  且各區塊皆不超過既定預算——通過率 100%。
  本 Feature 的「自動檢查」指**推播前的預算檢查**與**單元測試**兩者；
  全 Track × 全 Session 的 CI Gate 屬 F5，不在本 Feature 範圍（見 Out of Scope）。
  計算口徑依 FR-006a。
- **SC-003**: 版面可讀性驗收，以**實際收訊後的人工確認**為準，判準如下：
  - **裝置基準**：一般手機直式螢幕（≈ 6 吋、預設字級）的 Discord 行動版客戶端。
  - **可讀性**：主要觀念段落（觀念精華）不需捲動兩次以上即可讀完。
  - **辨識度**：能一眼看出「今天要做的題目是哪幾題」。
  - **整體判定**：須明確回答「這讀起來像一堂課」。
  - **判定者與時機**：由本 Feature 的驗收者（使用者本人）於首次真實推播成功後當次判定。
  - **不通過的處置**：視為版面缺陷，MUST 調整教材內容或版面後重新驗收；
    此判定 MUST NOT 阻擋其他 Success Criteria 的驗收結論。
- **SC-004**: 同一天（台北時區）內觸發 2 次，頻道只收到 1 則課程訊息；進度只前進 1 課。
- **SC-005**: 連續 3 次（以強制模式或跨日）觸發後，收到 3 則訊息且其課程序號依序為 1、2、3，
  不重複、不跳號；第 4 次觸發因課表用盡而明確報錯，不回頭重推第 1 課。
- **SC-011**: 一位未參與開發的使用者，依照環境建置說明文件操作，可在 30 分鐘內完成
  狀態分支初始化與推播頻道設定，並成功收到第一則課程訊息，過程中不需詢問實作者。
- **SC-006**: 推播失敗的情境下，頻道收到 1 則紅色告警訊息，且該 Track 的進度序號維持不變（0 課前進）。
- **SC-007**: 預覽模式觸發後，頻道新增訊息數為 0，狀態分支新增提交數為 0，而執行紀錄中可看到完整渲染結果。
- **SC-008**: 在完全沒有提供任何 LLM 服務憑證的環境下，每日流程端到端成功執行（成功率 100%）。
- **SC-009**: 主要開發分支上自動產生的進度提交數為 0；所有進度提交皆位於專用狀態分支。
- **SC-010**: 對同一課程物件重複渲染 100 次，產出的推播內容 100% 逐字元相同。

## Assumptions

- **單一 Track 驗收、多 Track 形態實作**：本 Feature 只需設定一個 Track（Foundation）的頻道即可完成驗收；
  但處理流程 MUST 以「逐一處理多個已啟用 Track」的形態實作（迴圈只是恰好跑一個元素），
  避免 F6 全面重寫。多 Track 的失敗隔離**驗收**留待 F6。
- **Session 類型只做 concept 版面**：本 Feature 的最小渲染只實作 concept 類版面；
  practice / challenge / review / rest 版面留待 F5。
- **無正式 schema 與 DAG**：教材以手寫方式提供、課表以硬編方式提供，兩者皆不經 schema 驗證；
  正式的 frontmatter schema、DAG 建置與驗證屬 F2 範圍。教材**會被實際解析**（FR-004a），
  但解析只認固定區塊的存在與內容，不對 metadata 做型別 / 值域驗證。
- **學習路徑（昨天/今天/明天）在本 Feature 為硬編對照表**：依課程序號查表取得三個鄰近觀念名稱
  （見 FR-007a）；正式取自 DAG 的 prerequisite / next 屬 F2 之後。
- **三個 Session 內容相同是刻意的**：本 Feature 驗證的是鏈路、去重與版面，不是內容多樣性；
  連續三天收到同一堂課屬預期行為，不列為缺陷。
- **課表走完即失敗**：3 個 Session 用完後不循環、不自動延伸，改為 fail loud，提醒這是臨時課表。
- **環境建置為「有文件的手動步驟」**：本 Feature 交付說明文件與初始資料樣板，實際執行由使用者手動完成；
  不提供自動化建置腳本（一次性用途不值得長期維護，且涉及分支與外部服務的破壞性操作）。
- **臨時產物一律標示臨時性**：本 Feature 的所有臨時產物 MUST 在其檔案內標示「臨時性」與「接手的 Feature」，
  規則一致適用，不因產物型態（教材 / 課表 / 資料檔 / 對照表）而異。清單見下方〈臨時產物與交棒〉。
- **臨時產物的存放位置刻意不對稱**：最小題庫置於既定的題庫路徑（F3 只需擴充資料）；
  但硬編課表 **MUST NOT** 置於課表生成物的路徑——憲章明文禁止手寫該路徑的檔案，
  且手寫檔會污染 F4 生成器的 byte-identical 驗證。手寫教材則置於教材產物路徑，
  理由是唯有如此才能驗證到真正要用的讀取路徑（此為 walking skeleton 的目的）；
  憲章禁止的是「手改**既有**生成物」，而本 Feature 階段產線尚未存在、無生成物可改。
- **無 CI Gate 期間的替代把關**：本 Feature 不建立 CI 內容 Gate（屬 F5）。
  期間的內容把關由三者共同承擔：推播前的預算檢查（FR-006）、單元測試（含渲染與預算）、
  以及以預覽模式實際檢視版面。教材或版面變更後 MUST 至少執行一次預覽模式確認未超限。
- **時區固定為 Asia/Taipei**：所有「今天」的判斷一律以台北時區日曆日為準，不提供時區設定項。
- **失敗告警發送對象與責任歸屬**：某 Track 的失敗告警發至該 Track 自己的頻道；整體流程層級的失敗告警發至
  第一個已設定的頻道。兩者**皆由推播程式以同一套告警渲染邏輯發出**（FR-010a）；排程平台只保留一道
  極簡純文字的最後防線通知，涵蓋程式根本沒能啟動的情境（FR-010b）。

## 臨時產物與交棒

本 Feature 刻意交付一批**用完即丟**的產物，用以先打穿鏈路。為避免這些產物在後續 Feature 中與正式產物
並存而形成技術債，逐項列出其接手者與淘汰條件：

| 臨時產物 | 需求 | 接手 Feature | 淘汰條件 |
|---|---|---|---|
| 手寫教材（一篇） | FR-001 | **F7** | 內容產線生成並通過品質 Gate 後，由生成物取代 |
| 硬編 3-Session 課表 | FR-002 | **F4** | 課表生成器產出正式課表後移除 |
| 最小題庫（3 題） | FR-003a | **F3** | 擴充為完整題庫，資料檔延續使用（**不需移除，只需擴充**） |
| 學習路徑硬編對照表 | FR-007a | **F2** | DAG 建立後改由 prerequisite / next 取得，對照表移除 |

**交棒規則（MUST）**：
- 上述每一項 MUST 在其檔案內明確標示臨時性與接手 Feature。
- 接手 Feature 完成時，MUST 一併**移除**被取代的臨時產物（除「僅需擴充」者），
  MUST NOT 讓臨時產物與正式產物並存——並存會使「哪一份是真實來源」變得不確定。
- 接手 Feature 的驗收 MUST 包含「對應臨時產物已移除或已被正式來源取代」這一項。

**相對地，本 Feature 交付的下列產物為永久資產**，後續 Feature 應在其上擴充而非重建：
工程鷹架（建置 / 測試設定）、組裝與渲染的模組邊界、狀態儲存與推進邏輯、推播與失敗處理、
排程 workflow 與去重機制、一次性環境建置文件。

## Out of Scope（本 Feature 明確不做）

- Curriculum 骨架、Concept frontmatter schema、DAG 建置與驗證（F2）。
- 完整題庫資料、題庫 schema 驗證與 Concept ↔ Problem 逆向對應（F3）。
  （本 Feature 僅提供 3 題的最小資料檔供讀取，見 FR-003a。）
- 課表生成器、Track 參數與 Overlay（F4）。
- Lesson Compiler 的完整解析、全 Session 類型版面、CI 內容 Gate（F5）。
- 多 Track 端到端與失敗隔離的正式驗收（F6）。
- **推播請求本身的自動重試與限流退避（F6）**：本 Feature 的推播失敗一律直接視為該 Track 失敗，
  不重試——雙排程（主推 / 補跑）已提供當日的補救機會。
  （FR-017 的重試僅適用於**狀態分支的提交衝突**，與推播請求無關。）
- 任何 LLM 內容產線（F7）。
- Weekly Review 素材、語錄池（F8）；GitHub Pages 與互動化（F9 / F10）。

## Dependencies

- 一個可用的 Discord 帳號與伺服器（建立頻道與推播位址所需；建立步驟由 FR-024 的文件涵蓋）。
- 版本控制平台的排程執行能力、機密管理機制，以及對版本庫的寫入權限（用於提交狀態分支）。
- 使用者願意依 FR-024 的文件執行一次性環境建置（狀態分支初始化、頻道與機密設定）。
